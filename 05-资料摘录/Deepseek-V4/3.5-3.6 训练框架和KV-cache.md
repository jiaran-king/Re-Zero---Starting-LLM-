# 3.5 Training Framework 总体背景

论文说，DeepSeek-V4 的训练框架继承自 DeepSeek-V3 的大规模训练基础设施，但 V4 引入了几个新东西：

```text
Muon optimizer
mHC
Hybrid attention: CSA + HCA
1M context training
```

这些东西让训练更难：

```text
Muon 不像 AdamW 那样容易做 ZeRO 分片
mHC 会扩大 residual stream，增加激活和 pipeline 通信
CSA/HCA 会压缩 KV，但压缩边界和 CP 切分会冲突
1M context 下 activation memory 非常大
```

所以 3.5 不是在讲一个新算法，而是在讲：

> 为了让 DeepSeek-V4 真的能训练起来，训练系统做了哪些适配。

---

# 3.5.1 Efficient Implementation of Muon

## 1. 问题：Muon 和 ZeRO 天然冲突

DeepSeek-V4 大部分参数使用 **Muon optimizer**。

Muon 的特点是：  
它对一个完整的参数矩阵做更新，需要拿到完整的 gradient matrix，然后进行类似正交化的 Newton-Schulz 迭代。

而 ZeRO 的思想是：

> 把 optimizer state、gradient、parameter 分散到多个 rank 上，减少单卡显存。

这对 AdamW 很自然，因为 AdamW 基本是逐元素更新：

```text
每个参数元素都有自己的 m、v
每个 rank 拿一部分参数就能更新这一部分
```

但 Muon 不一样。Muon 的更新不是单个元素独立完成的，而是针对整个矩阵：

```text
完整 gradient matrix
        ↓
momentum
        ↓
Newton-Schulz orthogonalization
        ↓
完整矩阵更新
```

所以如果一个矩阵被 ZeRO 切碎到很多 rank 上，每个 rank 只看到一小块，就没法独立完成 Muon 更新。

这就是核心矛盾：

```text
ZeRO 想切碎矩阵
Muon 想看完整矩阵
```

---

## 2. Dense 参数：限制 ZeRO 并行规模 + knapsack 分配

对于 dense parameters，DeepSeek-V4 没有让 ZeRO 无限切，而是：

```text
限制 ZeRO parallelism 的最大规模
```

然后用 **knapsack algorithm** 把不同参数矩阵分配给这些 rank，让每个 rank 管理的参数量大致均衡。

直观理解：

```text
不是把一个矩阵切成很多碎片
而是把完整矩阵作为单位，分配给不同 rank
```

比如有很多矩阵：

```text
W1, W2, W3, W4, W5...
```

系统会尽量把它们装进不同 rank 的“桶”里，使每个桶差不多大。

这样每个 rank 可以拿到某些完整矩阵，从而独立执行 Muon 更新。

---

## 3. Padding：让 reduce-scatter 高效

论文还说，每个 rank 的 bucket 会 padding 到和最大 bucket 一样大，这样方便做高效的 reduce-scatter。

这样会带来一点额外显存开销，但论文说在他们的设置里通常小于 10%。

可以理解为：

```text
为了通信规整，允许每个桶补一点空白
```

这是一种典型的系统工程 trade-off：

> 用少量额外内存，换取通信和实现上的高效。

---

## 4. 当 data parallel 更大时怎么办？

如果总体 data parallel size 超过 Muon 的 ZeRO 限制，DeepSeek-V4 不会继续扩大单个 Muon ZeRO group。

更准确地说，它会把所有 DP ranks 分成多个不超过上限的小 group：

```text
总 DP size 很大
    ↓
拆成多个固定大小的 Muon/ZeRO groups
    ↓
每个 group 内部按完整矩阵分配参数
    ↓
不同 group 之间冗余执行同一套 Muon update
```

这里要区分两层：

```text
group 内部：不同 rank 负责不同完整矩阵
group 之间：相同参数矩阵的 Muon update 会被重复计算
```

也就是说，不是让更多 rank 一起把同一个 Muon 矩阵切得更碎，而是复制出多个 Muon optimizer group。这样总 DP size 可以继续扩大，但单个 Muon group 仍然保持在可控规模内，避免破坏 Muon 对完整矩阵的需求。

这是一个“用少量重复计算，换取矩阵完整性和通信简单性”的选择。

---

## 5. MoE 参数：按 expert 独立优化

MoE 参数的情况不一样。

因为 MoE 有大量 expert，每个 expert 自己有 up projection、gate projection、down projection 等矩阵。

论文的做法是：

```text
每个 expert 独立优化
```

然后把所有 expert 的矩阵按类型展开：

```text
所有 experts 的 down projection 矩阵
所有 experts 的 up projection 矩阵
所有 experts 的 gate projection 矩阵
```

再把这些矩阵 flatten 成长向量进行分配，但有一个重要约束：

> padding 时要保证不会把一个 logically independent matrix 切开。

也就是说，矩阵仍然保持完整性。

由于 expert 数量很多，天然就有很多完整矩阵可以分配，因此 MoE 参数不需要像 dense 参数那样限制 ZeRO parallelism，padding 开销也可以忽略。

---

## 6. 相同形状参数合并，批量做 Newton-Schulz

论文还提到一个优化：

```text
consecutive parameters of identical shape will be automatically merged
```

也就是连续的、形状相同的参数会被自动合并，然后批量执行 Newton-Schulz 迭代。

这很重要，因为单个小矩阵单独跑可能利用率不高；批量跑可以提高硬件利用率。

直观上是：

```text
很多同形状小任务
        ↓
合成一个 batched 任务
        ↓
GPU 利用率更高
```

---

## 7. BF16 同步 MoE gradients，减少通信量

论文观察到 Muon 的 Newton-Schulz 迭代用 BF16 matmul 也稳定。

因此，他们进一步把 MoE gradients 在 data-parallel ranks 之间同步时量化到 BF16。

效果是：

```text
通信量减半
```

因为原本如果用 FP32，同步一个 gradient 要 32 bit；BF16 只要 16 bit。

但低精度累加容易引入误差，所以他们没有直接用普通 tree/ring reduce-scatter，而是设计了两阶段通信：

```text
第一阶段：all-to-all 交换 local gradients
第二阶段：每个 rank 在本地用 FP32 求和
```

这样既减少通信量，又避免低精度加法不断累积误差。

---

## 3.5.1 小结

这一小节可以概括成：

> Muon 需要完整矩阵，传统 ZeRO 喜欢切矩阵。DeepSeek-V4 通过“完整矩阵级别分配 + bucket padding + 冗余 DP 计算 + MoE expert 独立优化 + BF16 gradient 同步”来让 Muon 在超大规模训练里可用。

关键逻辑是：

```text
AdamW：逐元素优化，适合细粒度 ZeRO
Muon：矩阵级优化，需要保留完整矩阵
```

所以 DeepSeek-V4 的系统设计围绕一个原则：

```text
不要破坏 Muon 的矩阵完整性
```

---

# 3.5.2 Cost-Effective and Memory-Efficient Implementation of mHC

## 1. mHC 带来的额外成本

前面架构部分讲过，mHC 会扩展 residual stream。

普通 residual stream 可能是：

```text
x ∈ R^d
```

mHC 会扩成：

```text
X ∈ R^{n_hc × d}
```

这带来两个直接成本：

```text
activation memory 增加
pipeline stage 之间通信量增加
```

因为每层之间传的不再只是一个 hidden state，而是更宽的 residual state。

---

## 2. 优化一：为 mHC 设计 fused kernels

论文首先提到，他们为 mHC 的训练和推理都设计了 fused kernels。

这样做的目的和 3.2 的 TileLang 思路一致：

```text
减少中间 tensor materialization
减少 kernel launch
减少显存读写
提升吞吐
```

mHC 里有很多线性映射、归一化、约束变换，如果都用普通 PyTorch ATen operator，会产生大量小 kernel 和中间激活。

fused kernel 能把这些操作合在一起。

---

## 3. 优化二：选择性 recomputation

mHC 会带来更大的 activation memory，所以需要 checkpointing / recomputation。

但它不是简单地“全部重算”，而是有选择地重算。

论文说他们会：

```text
recompute most hidden states between layers
recompute all normalized layer inputs
avoid recomputation of compute-intensive operations
```

这句话非常关键。

它的意思是：

> 便宜的中间结果可以不存，反向时重算；昂贵的计算结果尽量存下来，不要反复重算。

也就是在 memory 和 compute 之间做平衡。

可以理解为：

```text
便宜但占内存的东西：丢掉，反向重算
贵的计算：尽量保留，避免重算
```

---

## 4. 优化三：调整 DualPipe 1F1B overlapping

DeepSeek 系列训练里使用了 pipeline parallelism。  
mHC 增加了 pipeline stage 之间的通信量，所以原来的 overlapping 方式可能不再最优。

论文说他们调整了 **DualPipe 1F1B overlapping scheme**，让 mHC 中的一些操作可以并发执行。

这里不用深入 DualPipe 细节，抓住核心即可：

> mHC 增加通信后，训练框架重新安排 pipeline 内部的执行顺序，让通信和计算继续尽量 overlap。

---

## 5. 最终开销

通过这些优化，论文说 mHC 的 wall-time overhead 被限制到：

```text
only 6.7% of the overlapped 1F1B pipeline stage
```

也就是说，虽然 mHC 在架构上明显更复杂，但工程优化之后，额外训练时间开销控制在比较小的范围内。

---

## 3.5.2 小结

这一小节可以概括成：

> mHC 提升模型表达能力，但会增加 activation memory 和 pipeline communication。DeepSeek-V4 通过 fused kernels、选择性 recomputation、调整 pipeline overlap，把 mHC 的训练开销压到可接受范围。

核心 trade-off 是：

```text
mHC 更强，但更贵
系统优化的目标是让它“强得值得，贵得可控”
```

---

# 3.5.3 Contextual Parallelism for Long-Context Attention

这一节是 3.5 里最重要也最容易困惑的部分。

它解决的是：

> 在 1M context 训练时，sequence 会被切到多个 rank 上；但 CSA/HCA 需要按 m 或 m' 个 token 做压缩。切分边界可能破坏压缩块，怎么办？

---

## 1. Conventional Context Parallelism 是什么？

Context Parallelism，简称 CP，通常是沿 sequence dimension 切分。

比如一个长序列：

```text
tokens: 0 ... 999999
```

如果有 4 个 CP ranks，可能切成：

```text
rank 0: token 0      ~ 249999
rank 1: token 250000 ~ 499999
rank 2: token 500000 ~ 749999
rank 3: token 750000 ~ 999999
```

每个 rank 只负责一段连续 tokens。

这对普通 attention 已经很复杂；对 CSA/HCA 更复杂。

---

## 2. 挑战一：压缩后的 KV 长度不规则

CSA/HCA 会把多个 token 压成一个 KV entry。

比如 CSA compression rate：

```text
m = 4
```

意思是每 4 个 token 压成 1 个 compressed KV entry。

如果某个 rank 有 s 个 token，理想情况下压缩后长度是：

```text
s / m
```

但训练样本往往是 packed sequence，由多个不同样本拼起来。每个 sequence 要独立压缩，尾部不足 m 的 token 会被丢弃或者不能形成完整压缩块。

所以实际 compressed KV length 可能：

```text
小于 s / m
并且不同 rank 之间长度不同
```

这会让后续 all-gather 和 attention kernel 很难处理，因为每个 rank 产出的 compressed KV 数量不一致。

---

## 3. 挑战二：压缩块可能跨 rank 边界

压缩需要连续 m 个 KV entries。

假设：

```text
m = 4
```

某个压缩块可能需要：

```text
token 249998, 249999, 250000, 250001
```

但 token 249998、249999 在 rank 0，token 250000、250001 在 rank 1。

这就出现了边界问题：

```text
一个压缩块需要的 token 分布在两个 CP rank 上
```

如果 rank 1 只看自己的本地 tokens，它就没法正确压缩这个块。

---

# DeepSeek-V4 的两阶段通信方案

论文提出了一个 two-stage communication approach。

---

## 第一阶段：每个 rank 把最后 m 个 uncompressed KV 发给下一个 rank

具体来说：

```text
rank i sends its last m uncompressed KV entries to rank i+1
```

这样 rank i+1 在压缩自己开头附近的 token 时，就能看到前一个 rank 的尾部 tokens。

直观理解：

```text
rank i:      [ ... a b c d ]
rank i+1:    [ e f g h ... ]

rank i 把 a b c d 发给 rank i+1
rank i+1 就可以处理跨边界压缩块
```

这样解决了“压缩块跨 rank 边界”的问题。

---

## 第二阶段：all-gather compressed KV，然后 select-and-pad

每个 rank 压缩后，会产生固定长度：

```text
s / m + 1
```

其中可能包含 padding entries。

然后所有 CP ranks 做 all-gather，把本地 compressed KV 收集起来。

之后，系统使用一个 fused select-and-pad operator，把它们整理成完整 compressed KV 集合，总长度为：

```text
cp_size · s / m
```

多余的 padding entries 会放到尾部。

可以理解为：

```text
各 rank 本地压缩结果
        ↓ all-gather
收集所有 compressed KV
        ↓ fused select-and-pad
整理成 attention kernel 能直接使用的规整格式
```

---

## CSA 和 HCA 的 visible range 怎么确定？

论文最后补充：

对于 HCA 和 CSA indexer，某个 query 能看到哪些 compressed KV entries，可以根据规则预先计算。

而对于 CSA sparse attention，top-k selector 会明确给出每个 query 可见的 compressed KV indices。

也就是说：

```text
HCA / CSA indexer:
    visible range 可以规则化预计算

CSA sparse attention:
    top-k selector 直接给出可见 indices
```

---

## 3.5.3 小结

这一小节可以概括为：

> Context Parallelism 把长序列切到不同 rank 上，但 CSA/HCA 的压缩需要跨 token 连续性。DeepSeek-V4 通过“先交换边界 uncompressed KV，再 all-gather compressed KV 并 select-and-pad”的两阶段通信，让压缩 attention 可以在 CP 下工作。

最关键的理解是：

```text
CP 切分破坏了压缩块的连续性
所以先补齐边界信息
再统一整理压缩后的 KV
```

# 3.5.4 Extended Automatic Differentiation for Flexible Activation Checkpointing

这一节讲的是 activation checkpointing。

---

## 1. 传统 activation checkpointing 的问题

大模型训练时，forward 会产生很多 activations。  
如果全部存下来，显存爆炸；如果全部不存，backward 时要大量重算，训练变慢。

Activation checkpointing 的目标是：

```text
少存一些 activation
backward 时按需重算
```

传统做法通常是 module-level：

```text
整个 Transformer block 存或不存
整个 attention module 存或不存
整个 FFN module 存或不存
```

问题是粒度太粗。

一个 module 里面有些 tensor：

```text
很占内存，但重算便宜
```

另一些 tensor：

```text
不太占内存，但重算很贵
```

如果只能整个 module 一起处理，就很难达到最优 trade-off。

---

## 2. 手写 forward/backward 又太复杂

另一种做法是手动实现整个 layer 的 forward 和 backward，精确控制哪些 tensor 存、哪些 tensor 重算。

这样确实灵活，但代价是：

```text
开发复杂
容易出错
维护成本高
失去自动微分便利
```

DeepSeek-V4 的模型已经很复杂，如果每个层都手写 backward，工程成本会非常高。

---

## 3. DeepSeek-V4 的做法：tensor-level checkpointing + autograd support

论文提出的是：

> tensor-level activation checkpointing with automatic differentiation support

也就是开发者只需要实现 forward，然后对个别 tensor 做 annotation：

```text
这个 tensor 可以 checkpoint
这个 tensor backward 前可以 recompute
```

剩下的事情交给框架自动处理。

这比 module-level 更细：

```text
不是决定整个模块要不要重算
而是决定某个 tensor 要不要重算
```

---

## 4. TorchFX tracing + recomputation graph

框架使用 TorchFX trace 完整 computation graph。

对于每个被标注的 tensor，框架会做 backward traversal，找出为了重算这个 tensor 所需的最小子图。

论文把这个最小子图称为：

```text
recomputation graph
```

然后在 backward 逻辑里，在对应梯度计算前插入这个 recomputation graph。

流程可以理解为：

```text
forward graph
        ↓ TorchFX trace
完整计算图
        ↓ 找到被标注 tensor
反向遍历，找到最小重算子图
        ↓
backward 时插入重算逻辑
```

---

## 5. 没有额外训练开销

论文说，相比手写实现，这个设计在训练中没有额外 overhead。

其中一个细节是：

```text
直接释放 annotated tensor 的 GPU memory
重算后复用 storage pointer
不做 GPU memory copy
```

这说明它不是简单地重新分配一块新内存再复制，而是复用原来的存储位置，减少内存操作开销。

---

## 6. 自动去重：处理共享 storage 的 tensor

还有一个很实用的点：

有些 tensor 其实共享底层 storage，比如 reshape 前后的 tensor。

如果框架不知道这一点，可能会重复重算。

DeepSeek-V4 的框架在 graph tracing 时会跟踪 tensor 的 storage pointer，因此可以自动识别共享 storage 的 tensor，避免重复 recomputation。

这可以减轻开发者负担：

```text
开发者不用手动推理底层 storage aliasing
框架自动 deduplicate
```

---

## 3.5.4 小结

这一小节可以概括为：

> DeepSeek-V4 扩展了自动微分框架，让 activation checkpointing 从 module-level 细化到 tensor-level。开发者只需要标注 tensor，框架自动用 TorchFX 找到最小重算子图，并在 backward 中插入重算逻辑，从而在不手写 backward 的情况下获得细粒度显存优化。

核心价值是：

```text
接近手写 checkpointing 的灵活性
保留自动微分的开发效率
```

---

# 3.5 整体总结

3.5 讲的是 DeepSeek-V4 的训练系统如何支撑复杂架构。

可以整理成一张逻辑表：

| 新组件        | 带来的问题                         | 训练框架解决方式                                            |
| ---------- | ----------------------------- | --------------------------------------------------- |
| Muon       | 需要完整矩阵，和 ZeRO 分片冲突            | 矩阵级 bucket 分配、限制 ZeRO 并行、冗余 DP 计算                   |
| MoE + Muon | expert 参数巨大，通信量大              | expert 独立优化，BF16 gradient 同步，本地 FP32 求和             |
| mHC        | activation 和 pipeline 通信增加    | fused kernel、选择性 recomputation、调整 DualPipe overlap  |
| CSA/HCA    | 压缩 KV 和 context parallel 边界冲突 | 两阶段通信：边界 KV 交换 + all-gather/select-and-pad          |
| 1M context | activation memory 极大          | tensor-level checkpointing + 自动 recomputation graph |

一句话总结：

> 3.5 的核心不是提出新模型结构，而是让 DeepSeek-V4 的新结构在大规模训练中真正可行：Muon 能并行优化，mHC 开销可控，CSA/HCA 能支持 context parallel，activation checkpointing 足够细粒度。

从整个第 3 部分看，3.5 是承上启下的一节：

```text
3.1-3.4：kernel、通信、确定性、量化
        ↓
3.5：把这些组件整合进训练框架
        ↓
3.6：进一步进入推理框架和 KV cache 管理
```

我们继续看 **3.6 Inference Framework**。这一节不像 3.5 讲训练，而是讲：**DeepSeek-V4 在推理服务时，如何管理复杂的 KV Cache，尤其是如何支持 1M token 长上下文和共享前缀复用**。核心内容分两块：**3.6.1 KV Cache 结构与管理**，以及 **3.6.2 磁盘 KV Cache 存储**。

## 1. 为什么 3.6 要单独讲 KV Cache？

普通 Transformer 推理时，每生成一个新 token，都要 attention 到前面的历史 token。为了避免每一步都重新算历史 token 的 K/V，会把历史 token 的 Key 和 Value 缓存下来，这就是 **KV Cache**。

但 DeepSeek-V4 的 attention 不是普通 attention，而是混合结构：

- CSA：Compressed Sparse Attention
    
- HCA：Heavily Compressed Attention
    
- SWA：Sliding Window Attention
    
- CSA 里面还有 lightning indexer 的 KV
    
- CSA/HCA 还会有“暂时不能压缩的尾部 token 状态”
    

所以 DeepSeek-V4 的 KV Cache 不再是“每层、每个 token 存一份 K/V”这么简单，而是变成了很多种不同大小、不同更新规则、不同淘汰策略的 cache。论文把这叫做 **heterogeneous KV caches**，也就是“异构 KV 缓存”。

---

## 2. 3.6.1：KV Cache Structure and Management

这一小节的核心问题是：

> DeepSeek-V4 的 KV Cache 类型太多，不能直接套用传统 PagedAttention，所以需要重新设计 cache layout。

论文图 6 给出了整体布局。可以把它理解成两大块：

### 第一块：Classical KV Cache

这是给 **CSA/HCA 的压缩 KV** 用的。

CSA 和 HCA 都会把原始 token 压缩成更少的 KV entry：

- CSA：每 `m` 个 token 压缩成 1 个 compressed KV entry；
    
- HCA：每 `m'` 个 token 压缩成 1 个 compressed KV entry，而且 `m' >> m`。
    

论文后面的模型配置里，V4 常用的是：

- CSA 的压缩率 `m = 4`
    
- HCA 的压缩率 `m' = 128`
    

所以可以直观理解为：

- CSA：4 个原始 token 变 1 个压缩 KV；
    
- HCA：128 个原始 token 变 1 个压缩 KV。
    

Classical KV Cache 不是按单个 token 随便切块，而是按 `lcm(m, m')` 个原始 token 作为一个 cache block。`lcm` 是最小公倍数。若 `m = 4`，`m' = 128`，那么：

- `lcm(4, 128) = 128`
    
- 每个 cache block 覆盖 128 个原始 token；
    
- 对 CSA 来说产生 `128 / 4 = 32` 个压缩 KV；
    
- 对 HCA 来说产生 `128 / 128 = 1` 个压缩 KV。
    

这就是图 6 里写的：

- `k1 = lcm(m, m') / m`
    
- `k2 = lcm(m, m') / m'`
    

也就是说，一个 cache block 内部可以同时对齐 CSA 和 HCA 的压缩粒度。这样做的好处是：**不同 attention 层虽然压缩率不同，但可以被统一组织到同一种块结构里**。

---

### 第二块：State Cache

State Cache 主要服务两类东西：

第一类是 **SWA KV**，也就是 sliding window attention 最近窗口内的未压缩 K/V。SWA 只关心最近 `n_win` 个 token，所以它不像完整上下文 attention 一样无限增长。

第二类是 **CSA/HCA 里还没凑够压缩块的尾部 token**。例如 CSA 每 4 个 token 才能压成 1 个 compressed KV，如果当前只来了 2 个 token，那这 2 个 token 还不能压缩，必须先暂存在 buffer 里。HCA 同理，每 128 个 token 才压一次，那么尾部不足 128 个 token 的状态也要保留。

论文把 SWA 和这些尾部未压缩 token 看成一种 **sequence-specific state**，也就是“这个序列当前位置的状态”。因此它们不是放进普通的分页 KV cache，而是放进一个固定大小的 state cache pool 里，为每个请求动态分配。

可以这样记：

> Classical KV Cache 存“已经压缩好、可以长期复用的历史信息”；  
> State Cache 存“最近窗口和暂时还不能压缩的尾巴状态”。

---

## 3. 为什么不能直接用 PagedAttention？

传统 PagedAttention 假设比较规则：每层 KV cache 形状类似，按固定 block 管理就行。

但 DeepSeek-V4 破坏了这些假设，主要有两个原因。

第一，**不同 cache 有不同策略**。SWA 只保留最近窗口，CSA/HCA 存压缩历史，indexer 又有自己的 KV。它们的生命周期和淘汰规则不同，强行塞进一个统一 PagedAttention 结构会很别扭。

第二，**高性能 attention kernel 有对齐和块大小要求**。高性能 sparse attention kernel 通常希望每个 block 的 token 数固定、对齐 cache line、满足访存模式。如果 cache layout 和 kernel 没一起设计，就会拖慢性能。

所以论文强调：DeepSeek-V4 的 KV Cache layout 是和 sparse attention kernel **co-design** 的，也就是系统和算子联合设计。

---

## 4. 3.6.2：On-Disk KV Cache Storage

这一小节讲的是一个推理服务场景里的重要优化：**共享前缀复用**。

> [!note] 注意
> 磁盘 KV Cache 的主要目的不是把当前活跃请求的 KV 从显存搬到磁盘来做 swap，而是把已经算好的长前缀 KV 持久化下来，供后续相同 prefix 的请求复用。它可以顺带减少长期缓存对显存/内存的占用，但核心收益是减少重复 prefill。

很多请求可能有相同的长前缀，例如：

- 同一个长文档被多个用户提问；
    
- 同一个代码仓库被多轮 agent 反复分析；
    
- 同一套系统 prompt + 工具说明被大量请求复用；
    
- 长上下文任务中，前 90% 输入一样，后面问题不同。
    

如果每次请求都重新 prefill 整个长前缀，代价非常高。于是 DeepSeek-V4 会把 KV Cache 存到磁盘上。下次如果请求命中相同 prefix，就直接从磁盘读缓存，避免重复 prefill。

---

## 5. CSA/HCA 的磁盘缓存策略

对于 CSA 和 HCA，策略比较简单：

> 把所有 compressed KV entries 存到磁盘。

当新请求命中某个已缓存前缀时，就读取这个前缀对应的 compressed KV entries，直接复用。

但有一个细节：只复用到 **最后一个完整 compression block**。

原因是 CSA/HCA 的压缩是按块进行的。例如 HCA 每 128 个 token 压一次。如果一个 prefix 的最后只剩 50 个 token，不足 128 个，那么这 50 个 token 还没有形成完整压缩 KV。论文说，对于这些 tail incomplete block，还是需要重新计算，以恢复 uncompressed KV entries，因为它们没有被存成压缩 KV。

所以可以记成：

> 完整压缩块：直接读磁盘缓存。  
> 尾部不完整块：重新算。

---

## 6. SWA 的磁盘缓存为什么更麻烦？

SWA KV 是未压缩的，而且每层都有，所以体积很大。论文说，SWA KV 的体积大约是压缩后的 CSA/HCA KV 的 **8 倍**。因此不能简单粗暴地全部存，否则磁盘写入压力会很大。

于是论文提出三种 SWA 磁盘缓存策略。

### 策略一：Full SWA Caching

把所有 token 的 SWA KV 都存下来。

优点是：命中 prefix 时不需要重算，直接读最后 `n_win` 个 token 的 SWA KV 就行。

缺点是：写入量巨大，而且每次真正读取的只是最后窗口那一小段，大量写入的数据之后可能根本不会读到。所以这对 SSD 来说很不友好，是一种 write-intensive 的访问模式。

---

### 策略二：Periodic Checkpointing

每隔 `p` 个 token 存一次 checkpoint。每个 checkpoint 存的是当时最后 `n_win` 个 token 的 SWA KV。

命中 prefix 时：

1. 找到最近的 checkpoint；
    
2. 读出 checkpoint；
    
3. 从 checkpoint 之后的尾部 token 重新计算。
    

这个策略可以通过调节 `p` 来控制 trade-off：

- `p` 小：存得多，重算少；
    
- `p` 大：存得少，重算多。
    

这是比较折中的方案。

---

### 策略三：Zero SWA Caching

完全不存 SWA KV。

命中 prefix 时，只依赖已经缓存的 CSA/HCA compressed KV，然后重算一段尾部，恢复 SWA 状态。

论文给出的结论是：对于一个 `L` 层模型，只需要重算最后 `n_win × L` 个 token，就足够恢复最后 `n_win` 个 SWA KV。

这个策略存储成本最低，但重算最多。适合磁盘空间、写入带宽比较紧张，而算力相对可接受的部署场景。

---

## 7. 这一节的主线总结

3.6 的主线可以压缩成一句话：

> DeepSeek-V4 为了支持 CSA/HCA/SWA 混合 attention，在推理阶段设计了异构 KV Cache：压缩后的长期历史放入 classical KV cache，最近窗口和未压缩尾部状态放入 state cache；同时通过磁盘 KV Cache 复用共享前缀，减少长上下文 prefill 成本。

更具体地说：

- **CSA/HCA** 产生压缩 KV，适合长期保存和磁盘复用；
    
- **SWA** 产生未压缩窗口 KV，体积大，需要特殊策略；
    
- **尾部未满压缩块的 token** 暂时不能压缩，要放在 state cache；
    
- **cache block 按 `lcm(m, m')` 对齐**，让 CSA 和 HCA 能共享块组织；
    
- **KV layout 与 sparse attention kernel 联合设计**，避免因为 cache 管理拖慢 attention；
    
- **磁盘 KV cache** 用来复用 shared prefix，避免重复 prefill。
    

如果和上一节 3.5.3 对照看：

- 3.5.3 讲训练时 long-context attention 怎么在 CP ranks 之间通信、压缩、all-gather；
    
- 3.6 讲推理时 long-context attention 的 KV cache 怎么存、怎么复用、怎么落盘。
    

也就是说，**3.5 是训练长上下文的并行问题，3.6 是推理长上下文的缓存管理问题**。
