1.为什么有两组 a 和 b？
因为 CSA 的压缩是带重叠的。每个 compressed entry 实际会看当前块的一组 token 和前一个块的一组 token，总共涉及 2m 个位置。

这里的 **“带重叠”**，不是说压缩块的起点像 CNN 滑窗那样每次只滑一小步；而是说：

> **相邻两个 compressed entries 会共同用到同一段原始 token，只是用的是不同的投影分支：一个用 (C^a)，另一个用 (C^b)。**

论文原文对应公式是：CSA 先生成两组 KV entries：(C^a, C^b)，以及两组压缩权重 (Z^a, Z^b)。然后第 (i) 个 compressed entry (C_i^{Comp}) 会使用两段内容：当前块的 (C^a)，以及前一个块的 (C^b)。论文也明确说，每个 (C_i^{Comp}) 来自 (2m) 个 KV entries，但 (C_i^{Comp}) 用到的 (C^b) 索引，和 (C_{i-1}^{Comp}) 用到的 (C^a) 索引是重叠的，所以整体序列长度仍然压缩到 (1/m)。

我们用 (m=4) 举例最清楚。

原始 token 分块：

```text
Block 0: token 0,1,2,3
Block 1: token 4,5,6,7
Block 2: token 8,9,10,11
```

如果是普通不重叠压缩，大概会是：

```text
CComp_0 = 压缩 token 0,1,2,3
CComp_1 = 压缩 token 4,5,6,7
CComp_2 = 压缩 token 8,9,10,11
```

每个 compressed entry 只看自己对应的 4 个 token。

但 CSA 不是这样。它是：

```text
CComp_0 = 当前块 Block 0 的 C^a + 前一块 padding

CComp_1 = 当前块 Block 1 的 C^a + 前一块 Block 0 的 C^b

CComp_2 = 当前块 Block 2 的 C^a + 前一块 Block 1 的 C^b
```

所以 Block 0 实际上参与了两个 compressed entries：

```text
CComp_0 用了 Block 0 的 C^a
CComp_1 用了 Block 0 的 C^b
```

这就是 **重叠**。

换句话说：

```text
CComp_0 覆盖：Block 0
CComp_1 覆盖：Block 0 + Block 1
CComp_2 覆盖：Block 1 + Block 2
CComp_3 覆盖：Block 2 + Block 3
```

相邻的 compressed entries 在原始 token 范围上有交集。

---

一个更直观的图：

```text
原始 token 块：
[ B0 ][ B1 ][ B2 ][ B3 ]

压缩后的 entry：

CComp_0: [ B0 ]
CComp_1: [ B0 ][ B1 ]
CComp_2:      [ B1 ][ B2 ]
CComp_3:           [ B2 ][ B3 ]
```

所以它不是：

```text
[ B0 ][ B1 ][ B2 ][ B3 ]
  ↓    ↓    ↓    ↓
 C0   C1   C2   C3
```

而是更像：

```text
[ B0 ][ B1 ][ B2 ][ B3 ]
  ↓  ↘
 C0  C1
      ↓  ↘
      C1 C2
           ↓  ↘
           C2 C3
```

每个块既影响“自己的压缩 entry”，也影响“下一个压缩 entry”。

---

为什么要这样做？

因为如果每 4 个 token 直接压成 1 个，块边界会很硬：

```text
[ token 0 1 2 3 ] [ token 4 5 6 7 ]
```

token 3 和 token 4 明明相邻，但它们被分进两个完全独立的压缩块里，信息交互会变弱。

带重叠压缩的好处是：

> 让一个 compressed entry 不只看当前块，也能吸收前一个块的信息，从而缓解“块边界割裂”。

所以 CSA 的两个分支可以这样理解：

- (C^a)：当前块的表示；
    
- (C^b)：让当前块的信息被下一个 compressed entry 继续使用；
    
- (C_i^{Comp})：融合“当前块”和“前一块”的信息。
    

---

注意一个容易误会的点：  
虽然每个 (C_i^{Comp}) 看起来用了 (2m) 个 KV entries，但最终 compressed entries 的数量还是每 (m) 个 token 生成 1 个。

也就是：

```text
n 个 token  →  n/m 个 compressed entries
```

不是：

```text
n 个 token  →  n/(2m) 个 compressed entries
```

因为相邻 compressed entries 共享了一部分原始 token 范围。这个“共享范围”就是论文里说的 overlapped。

## 1. 这里的 MQA 是不是“多个 Query 头对应同一组 KV”？

是的。

在普通 **Multi-Head Attention, MHA** 里，一般是：

```text
Head 1: Q1, K1, V1
Head 2: Q2, K2, V2
Head 3: Q3, K3, V3
...
```

每个 head 都有自己的 (Q,K,V)。

但在 **MQA, Multi-Query Attention** 里，是：

```text
Head 1: Q1
Head 2: Q2
Head 3: Q3
...

所有 head 共享同一组 K/V
```

放到 CSA 里就是：

[  
o_{t,i} = CoreAttn(  
query=q_{t,i},  
key=C_t^{SprsComp},  
value=C_t^{SprsComp}  
)  
]

其中 (i) 是第 (i) 个 query head。也就是说：

```text
第 1 个 query head 用 q_{t,1}
第 2 个 query head 用 q_{t,2}
第 3 个 query head 用 q_{t,3}

但它们看的 key/value 都是同一组 C_t^{SprsComp}
```

论文这里明确说，每个 compressed KV entry 在 MQA 中同时作为 attention key 和 value。

所以你的理解可以写成：

> CSA 的 core attention 使用 MQA：每个 token 会生成多个 query heads，但这些 query heads 共享同一组 selected compressed KV entries。

---

## 2. “KV 共用一个表达”是什么意思？

这里有两层“共用”。

第一层是 **多个 query heads 共享同一组 KV**：

```text
q_{t,1}, q_{t,2}, ..., q_{t,n_h}
共同 attend 到 C_t^{SprsComp}
```

第二层是 **key 和 value 本身也共用同一个表示**：

```text
key   = C_t^{SprsComp}
value = C_t^{SprsComp}
```

普通 attention 里通常是：

[  
K = HW_K,\quad V = HW_V  
]

key 负责“匹配/寻址”，value 负责“被读取的内容”。

但 CSA 这里是：

[  
K = C^{Comp},\quad V = C^{Comp}  
]

同一个 compressed entry 既用来算相似度，也作为被加权求和的内容。

---

## 3. 这样不会影响性能吗？

会有表达能力上的取舍，但它的设计目标就是用更低成本换长上下文能力。

更细一点说：

### 普通 MHA 更灵活

普通 MHA 里每个 head 有自己的 (K,V)，表达能力最强：

```text
Head 1 可以用一套 key/value 关注语法信息
Head 2 可以用另一套 key/value 关注实体信息
Head 3 可以用另一套 key/value 关注位置关系
```

但代价是 KV cache 大、计算大。

---

### MQA 更省，但减少了 KV 多样性

MQA 让多个 query heads 共享 KV，所以 KV cache 小很多。

不过注意：虽然 KV 共享，**不同 query head 仍然可以产生不同 attention 分布**，因为它们的 query 不同：

[  
q_{t,1} \cdot C_s^{Comp}  
]

[  
q_{t,2} \cdot C_s^{Comp}  
]

即使 key 是同一组，query 不同，打分也可以不同。

所以不是所有 head 输出一样，而是：

```text
不同 head 用不同 query，从同一组 KV memory 中读取不同信息。
```

这就像：

> 多个人看同一本压缩版资料，但每个人带着不同问题去查，所以关注的段落不同。

---

### Key 和 Value 共用也会压缩表达，但很省

这一步确实比普通 attention 更激进。

普通 attention 是：

```text
key：用于判断相关性
value：用于承载内容
```

CSA 变成：

```text
CComp：既用于判断相关性，也用于承载内容
```

这可能损失一部分“寻址表示”和“内容表示”分离的能力。

但 DeepSeek-V4 用几个方式缓解这个问题：

1. (C^{Comp}) 本身不是简单池化，而是由 (C^a/C^b)、(Z^a/Z^b) 和位置偏置学出来的压缩表示；
    
2. 每个 query token 仍有很多 query heads，可以从不同角度读同一组 compressed entries；
    
3. 还有 sliding window branch 保留最近 token 的未压缩细节；
    
4. CSA 和 HCA 交错使用，HCA 提供更粗粒度的全局覆盖；
    
5. query 和 compressed KV 进入 core attention 前还会做 RMSNorm，提高稳定性。论文在 2.3.3 也提到这种 normalization 用来避免 attention logits 爆炸。
    

所以更准确的结论是：

> 这肯定是一个效率优先的设计，会牺牲一部分传统 attention 的表达自由度；但通过 learned compression、多 query heads、sliding window、CSA/HCA 混合等设计，把性能损失控制住，同时大幅降低长上下文成本。

---

## 4. 你可以这样记

CSA 的 core attention 是：

```text
多个 Query heads
        ↓
共同访问同一批 selected compressed KV entries
        ↓
这些 compressed entries 同时作为 Key 和 Value
        ↓
得到每个 head 的 attention output
```

一句话总结：

> **MQA = 多个 query heads，共享一组 KV memory；Shared Key-Value = 这组 memory 既负责匹配，也负责被读取。**

这一步的本质是：**把 attention 的“读取端”保留多头能力，把“记忆端”极限压缩。**
