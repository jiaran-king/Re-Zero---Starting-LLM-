# LLM-WIKI 使用指南

> [!note] 页面定位
> 这份文档面向日常使用。它说明你如何把这个 Obsidian 仓库当作 LLM-WIKI 来用：新增资料、查询知识、写回结论、维护图谱、整理项目和生成 Canvas。
>
> - 人负责：选择资料、提出问题、判断方向、确认修改
> - LLM 负责：读取规范、整理资料、抽取概念、更新主题页、维护索引和日志

---

## 1. 先理解这套仓库的四层

| 层级              | 目录                             | 作用                       |
| --------------- | ------------------------------ | ------------------------ |
| Source 层        | `05-资料摘录`、`07-待整理`             | 原始资料、PDF、论文、网页、对话摘录、临时材料 |
| Wiki 层          | `01-主题地图`、`02-概念笔记`            | 长期可复用的主题地图和概念页           |
| Project / Log 层 | `03-项目笔记`、`04-实验与日志`           | 项目上下文、实验过程、调试记录和阶段复盘     |
| Schema 层        | `00-首页与索引`、`AGENTS.md`、`06-模板` | 入口、规则、LLM 工作规范、笔记规范和模板   |

LLM-WIKI 的核心不是“把所有资料都放进一个文件夹”，而是把资料不断编译成可复用知识：

```text
资料进入仓库
→ LLM 按规则 ingest
→ 更新资料索引
→ 抽取概念
→ 更新概念页
→ 更新主题地图
→ 更新项目页或实验日志
→ 更新处理日志
→ 定期 Lint
```

## 2. 使用场景一：新增笔记或资料

### 2.1 先判断放在哪里

新增内容不要一开始就追求完美分类，先按成熟度放到合适层级。

| 新内容类型 | 推荐位置 | 说明 |
|---|---|---|
| PDF、论文、技术报告、网页摘录 | `05-资料摘录` | 作为 source 保留，不直接当作正式知识页 |
| 临时想法、还没判断归属的材料 | `07-待整理` | 临时 Inbox，不长期堆积 |
| 实验过程、调 bug 记录、阶段日志 | `04-实验与日志` | 保留过程和决策依据 |
| 项目文档、代码解析、项目总结 | `03-项目笔记` | 保留项目上下文 |
| 已经成熟的技术概念 | `02-概念笔记` | 必须补上主题归属和相关链接 |
| 主题导航、学习路线 | `01-主题地图` | 只承接主题和概念入口，不堆原始资料 |

### 2.2 推荐给 LLM 的指令

```text
请按 LLM-WIKI 工作流 ingest 这份资料。

执行前先读取：
1. AGENTS.md
2. 00-首页与索引/LLM工作规范/index.md
3. 00-首页与索引/LLM工作规范/LLM-WIKI工作流.md
4. 00-首页与索引/笔记规范/笔记整理规则.md

要求：
1. 不改写原始资料。
2. 判断资料类型和处理目标。
3. 更新 05-资料摘录/资料索引.md。
4. 提取可拆分概念。
5. 判断要新建还是更新概念页。
6. 如果更新 Wiki 层，同步更新主题地图。
7. 更新 `00-首页与索引/LLM工作规范/LLM-WIKI处理日志.md`。
8. 最后输出修改报告。
```

### 2.3 新增资料后的检查

新增资料后，至少确认三件事：

- `05-资料摘录/资料索引.md` 是否登记了这份资料
- 如果抽出了概念，`02-概念笔记` 中是否有对应页面
- 如果新增或更新了概念页，`01-主题地图` 是否承接了它

## 3. 使用场景二：查询知识

查询知识时，优先查 Wiki 层，而不是每次重新读 PDF 或从网上搜索。

### 3.1 推荐读取顺序

```text
AGENTS.md
→ 00-首页与索引/主页.md
→ 00-首页与索引/LLM工作规范/index.md
→ 相关主题页
→ 相关概念页
→ 必要时回查 05-资料摘录
```

### 3.2 常见问题入口

| 你想查的问题 | 优先入口 |
|---|---|
| LLM 全流程如何串起来 | `01-主题地图/0a.LLM全流程总览.md` |
| 主题导航从哪里开始 | `01-主题地图/0.LLM学习地图.md` |
| Transformer、Attention、BPE、位置编码、激活函数 | `01-主题地图/基础架构.md` |
| Scaling Law、预训练目标、数据、优化闭环 | `01-主题地图/预训练.md` |
| LoRA、QLoRA、Adapter、低成本微调 | `01-主题地图/参数高效微调.md` |
| SFT、RLHF、PPO、DPO、GRPO、Rollout、Expert Iteration、Reasoning RL | `01-主题地图/后训练与对齐.md` |
| KV Cache、Flash Attention、MQA/GQA、MLA、稀疏注意力、vLLM、PagedAttention | `01-主题地图/推理优化.md` |
| 显存、FLOPs、吞吐、并行、checkpoint、veRL、Ray、FSDP | `01-主题地图/训练系统工程.md` |
| VLM、Qwen2.5-VL、visual token、MRoPE、Chat template、tool calling | `01-主题地图/基础架构.md` |
| 已接入项目事实和阶段结果 | 先看 `03-项目笔记/` 和 `04-实验与日志/` 下对应项目目录 |

### 3.3 推荐给 LLM 的指令

```text
请基于我的 Obsidian LLM-WIKI 回答问题。

读取顺序：
1. AGENTS.md
2. 00-首页与索引/主页.md
3. 00-首页与索引/LLM工作规范/index.md
4. 相关主题页
5. 相关概念页
6. 必要时再回查 05-资料摘录

要求：
1. 优先基于仓库已有笔记回答。
2. 区分“仓库已有结论”和“你的推断”。
3. 如果发现知识库缺口，请列出应该补的页面。
4. 不要直接修改文件，除非我明确要求写回。

问题：
...
```

## 4. 使用场景三：把有价值的回答写回 Wiki

LLM-WIKI 的关键习惯是：高质量问答不要只留在聊天记录里，要沉淀回仓库。

适合写回的内容包括：

- 某个概念的新解释
- 两个方法的对比
- 项目经验的抽象总结
- 一条学习路线
- 一次排障经验的通用结论
- 对论文或报告的结构化理解

### 4.1 推荐给 LLM 的指令

```text
请把刚才讨论中有长期价值的结论写回我的 Obsidian LLM-WIKI。

要求：
1. 先判断应该写入哪个已有页面。
2. 优先更新已有概念页，不轻易新建。
3. 如果需要新建页面，先说明理由。
4. 如果更新了概念页，同步检查主题地图是否需要更新。
5. 更新 00-首页与索引/LLM工作规范/LLM-WIKI处理日志.md。
6. 最后输出修改报告。
```

### 4.2 写回时的判断标准

| 情况 | 处理方式 |
|---|---|
| 是一个独立技术点 | 更新或新建 `02-概念笔记` |
| 是一个主题导航判断 | 更新 `01-主题地图` |
| 是项目过程或实验结果 | 更新 `03-项目笔记` 或 `04-实验与日志` |
| 是资料阅读摘要 | 放入 `05-资料摘录`，并更新资料索引 |
| 只是临时想法 | 先放入 `07-待整理` |

## 5. 使用场景四：维护笔记和做 Lint

维护笔记时，优先做只读检查，再分批修复。不要一上来批量改全库。

### 5.1 什么时候做 Lint

- 新增 5 篇正式笔记后
- 整理完一个主题后
- 处理完一批资料后
- 面试或复习前
- 发现双链混乱、重复页面或待整理堆积时

### 5.2 推荐给 LLM 的只读 Lint 指令

```text
请按 LLM-WIKI 自检清单做一次只读检查。

读取：
1. AGENTS.md
2. 00-首页与索引/LLM工作规范/LLM-WIKI自检清单.md
3. 00-首页与索引/笔记规范/笔记整理规则.md

要求：
1. 只检查，不修改。
2. 按严重程度列问题。
3. 标出具体文件路径。
4. 给出分批修复建议。
```

### 5.3 常见维护项

| 维护项 | 目的 |
|---|---|
| 检查概念页是否有上位主题 | 防止孤立页 |
| 检查概念页是否有横向链接 | 防止知识断开 |
| 检查主题页是否承接新概念 | 防止概念找不到 |
| 检查资料是否登记到资料索引 | 防止资料失踪 |
| 检查 `07-待整理` 是否堆积 | 防止 Inbox 变成垃圾场 |
| 检查同义重复页 | 防止双链污染 |
| 检查伪死链 | 防止模板示例污染图谱 |
| 检查项目经验是否可沉淀 | 把项目经验变成可复用知识 |

## 6. 使用场景五：清理 `07-待整理`

`07-待整理` 是临时 Inbox，不应该长期堆积。

### 6.1 推荐给 LLM 的指令

```text
请检查 07-待整理，输出 Inbox 清理报告。

要求：
1. 不移动、不删除。
2. 判断每个文件应该流向哪里：
   - 05-资料摘录
   - 02-概念笔记
   - 03-项目笔记
   - 04-实验与日志
   - 继续留在 07-待整理
3. 说明理由。
4. 给出推荐处理顺序。
```

审核报告后，再让 LLM 分批执行：

```text
按刚才的 Inbox 清理报告执行第一批，只处理：
1. ...
2. ...

要求：
1. 保留原始内容。
2. 更新资料索引或主题地图。
3. 更新 `00-首页与索引/LLM工作规范/LLM-WIKI处理日志.md`。
```

## 7. 使用场景六：项目知识沉淀

项目笔记保留项目事实，但项目中反复出现的经验应该抽象到概念页。

### 7.1 推荐给 LLM 的指令

```text
请从项目笔记中抽取可复用知识。

读取：
1. AGENTS.md
2. 00-首页与索引/LLM工作规范/index.md
3. 相关项目目录
4. 相关实验日志
5. 相关概念页

要求：
1. 不改项目原始记录。
2. 区分“项目事实”和“可迁移技术理解”。
3. 找出可以抽象成概念页的经验。
4. 先输出报告，不直接修改。
```

### 7.2 适合沉淀的内容

| 项目中出现的内容 | 可能沉淀到 |
|---|---|
| LoRA 微调经验 | `02-概念笔记/LoRA.md` |
| KV Cache 加速实验 | `02-概念笔记/KV Cache.md` |
| tokenizer / control token 处理 | `02-概念笔记/BPE.md` |
| 显存、FLOPs、吞吐估算 | `02-概念笔记/大模型资源分析.md` |
| 结构化评测方法 | 新建或更新评测相关概念页 |
| 数据 pipeline 经验 | 项目页 + 可复用概念页 |

## 8. 使用场景七：生成或维护 Canvas

Canvas 是 Wiki 的可视化层，适合展示项目主线、训练流程、代码链路和数据流。

### 8.1 推荐给 LLM 的指令

```text
请根据这篇笔记生成 Obsidian Canvas。

执行前先读取：
1. 00-首页与索引/笔记规范/canvas.md
2. 00-首页与索引/笔记规范/绘图规则.md

要求：
1. 生成原生 .canvas JSON。
2. 文件放到 08-图片/。
3. 使用“主阶段节点 + 中间处理节点”的布局。
4. 不使用 Mermaid、SVG 或图片。
5. 生成后检查节点可读性、主线长度和布局留白。
```

### 8.2 修改已有 Canvas

```text
请读取 00-首页与索引/笔记规范/canvas.md，然后优化 08-图片/xxx.canvas。

目标：
1. 不改变主线含义。
2. 减少横向过长。
3. 提高中等缩放下可读性。
4. 保持伪菱形处理节点风格。
```

## 9. 推荐使用节奏

### 每天

```text
新资料 / 新想法 / 新实验
→ 放入 05、07、03 或 04
→ 不急着整理完美
```

### 每 2-3 天

```text
让 LLM 处理一个小批次资料
→ 更新资料索引
→ 抽概念
→ 更新主题页
→ 更新处理日志
```

### 每完成一个主题或项目阶段

```text
做一次只读 Lint
→ 你审核报告
→ 分批修复
```

### 每次复习或面试前

```text
从主题地图或项目页出发
→ 让 LLM 生成复习路线、追问题、知识缺口
```

## 11. 一句话总结

把这个仓库当成一个长期演化的知识系统：

```text
05 / 07 是输入队列
01 / 02 是正式 Wiki
03 / 04 是项目事实和过程
00 / AGENTS.md 是操作系统
```

以后不要只说“帮我总结一下这份资料”，而是说：

```text
请把这份资料 ingest 进我的 LLM-WIKI。
```

不要只说“这个问题怎么理解”，而是说：

```text
请基于我的 LLM-WIKI 回答，并判断是否需要写回知识库。
```

不要只说“我的笔记乱不乱”，而是说：

```text
请按 LLM-WIKI 自检清单做只读 Lint。
```
